# Warehouse Backend

This package implements warehouse management for the MMS backend. It provides secured REST endpoints for creating, reading, updating, filtering, and deleting warehouses.

The API base URL is:

```text
http://localhost:8081/api/v1/warehouses
```

## How the module works

A request moves through the backend in this order:

```text
Postman or frontend
       |
       | HTTP request + Keycloak bearer token
       v
WarehouseController
       |
       | validated request DTO
       v
WarehouseService
       |
       | business rules and transaction
       v
WarehouseRepository
       |
       | JPA / SQL
       v
PostgreSQL warehouses table
```

The response travels back through the same layers and is converted to `WarehouseResponse` JSON.

### Package files

| File | Responsibility |
| --- | --- |
| `Warehouse.java` | Maps the Java object to the PostgreSQL `warehouses` table. |
| `WarehouseController.java` | Defines URLs, HTTP methods, status codes, and permitted roles. |
| `WarehouseService.java` | Applies business rules and controls database transactions. |
| `WarehouseRepository.java` | Reads and writes warehouse data using Spring Data JPA. |
| `dto/CreateWarehouseRequest.java` | Defines and validates the JSON accepted by `POST`. |
| `dto/UpdateWarehouseRequest.java` | Defines and validates the JSON accepted by `PUT`. |
| `dto/WarehouseResponse.java` | Defines the JSON returned to Postman and the frontend. |
| `../shared/GlobalExceptionHandler.java` | Converts validation and business exceptions into JSON errors. |

## Request lifecycle example

When Postman sends `POST /api/v1/warehouses`:

1. Spring Security validates the bearer token with Keycloak.
2. `@PreAuthorize` checks whether the token contains an allowed realm role.
3. Spring converts the JSON body into `CreateWarehouseRequest`.
4. Jakarta Validation checks required fields, lengths, code format, and capacity.
5. `WarehouseService` checks that the warehouse code is unique.
6. The service creates a `Warehouse` entity and starts a database transaction.
7. `WarehouseRepository` inserts the entity into PostgreSQL.
8. The service calculates `used` and `items` from the `inventory` table.
9. The controller returns `201 Created`, a `Location` header, and the warehouse JSON.

If any step fails, the transaction is rolled back and an appropriate HTTP error is returned.

## Database and response fields

| API field | Database source | Meaning |
| --- | --- | --- |
| `id` | `warehouses.id` | Unique warehouse code, such as `WH-Main`. |
| `name` | `warehouses.name` | Display name. |
| `location` | `warehouses.location` | Physical location. |
| `type` | `warehouses.warehouse_type` | Warehouse category, such as `General` or `Cold Chain`. |
| `capacity` | `warehouses.capacity` | Maximum storage capacity. |
| `manager` | `warehouses.manager_name` | Responsible manager. |
| `active` | `warehouses.active` | Whether the warehouse is available for operations. |
| `used` | Sum of `inventory.on_hand` | Current stock quantity stored in the warehouse. |
| `items` | Count of `inventory` rows | Number of different inventory records in the warehouse. |
| `createdAt` | `warehouses.created_at` | Creation time generated by the backend. |
| `updatedAt` | `warehouses.updated_at` | Last update time generated by the backend. |

Clients do not send `used`, `items`, `createdAt`, or `updatedAt`; the backend calculates them.

## Endpoints and roles

| Method | URL | Success | Allowed realm roles |
| --- | --- | --- | --- |
| `GET` | `/api/v1/warehouses` | `200 OK` | `admin`, `mms_user`, `inventory_manager`, `store_keeper`, `viewer` |
| `GET` | `/api/v1/warehouses/{id}` | `200 OK` | `admin`, `mms_user`, `inventory_manager`, `store_keeper`, `viewer` |
| `POST` | `/api/v1/warehouses` | `201 Created` | `admin`, `inventory_manager`, `store_keeper` |
| `PUT` | `/api/v1/warehouses/{id}` | `200 OK` | `admin`, `inventory_manager`, `store_keeper` |
| `DELETE` | `/api/v1/warehouses/{id}` | `204 No Content` | `admin`, `inventory_manager` |

Use `GET /api/v1/warehouses?active=true` to return only active warehouses, or `active=false` to return only inactive warehouses.

## Validation rules

- `id` is required, is at most 50 characters, and accepts letters, numbers, hyphens, and underscores.
- `name`, `location`, `type`, and `manager` are required.
- `capacity` is required and must be greater than zero.
- `active` is optional during creation and defaults to `true`.
- `PUT` updates the warehouse identified by the URL; it does not change its `id`.

### 3. Create a Postman environment

1. Open Postman.
2. Select **Environments** and create an environment named `MMS Local`.
3. Add `baseUrl` with the value `http://localhost:8081`.
4. Save the environment and select `MMS Local` in the top-right environment selector.
5. Create a collection named `MMS Warehouse`.

Requests in this guide use `{{baseUrl}}`, which Postman replaces with the environment value.

### 4. Configure Keycloak OAuth2

Open the `MMS Warehouse` collection and select **Authorization**. Enter:

| Postman setting | Value |
| --- | --- |
| Type | `OAuth 2.0` |
| Add auth data to | `Request Headers` |
| Grant Type | `Authorization Code (With PKCE)` |
| Callback URL | `https://oauth.pstmn.io/v1/callback` |
| Auth URL | `http://localhost:8080/realms/erp/protocol/openid-connect/auth` |
| Access Token URL | `http://localhost:8080/realms/erp/protocol/openid-connect/token` |
| Client ID | `mms-postman` |
| Client Secret | Leave empty |
| Code Challenge Method | `SHA-256` |
| Scope | `openid profile email` |

Then:

1. Select **Get New Access Token**.
2. Log in with username `erp-admin` and password `change-me`.
3. Set a permanent password if Keycloak requests it.
4. Select **Use Token**.
5. Save the collection.

Each request should use **Inherit auth from parent**. The access token lasts five minutes; request a new token when it expires.

Send the `Create Warehouse` request from step 5 again without changing its ID.

Expected status: `409 Conflict` with a message similar to:


### 11. Delete the test warehouse

Create and send:

```text

```

Expected status: `204 No Content`, with an empty response body.

Send `GET /api/v1/warehouses/WH-POSTMAN` again. Expected status: `404 Not Found`.

## HTTP errors

| Status | Meaning | What to check |
| --- | --- | --- |
| `400 Bad Request` | JSON or validation is invalid. | Check `fieldErrors` and send all required fields. |
| `401 Unauthorized` | Token is missing, invalid, or expired. | Use the collection token and select **Inherit auth from parent**. |
| `403 Forbidden` | Token is valid but the user lacks permission. | Check the user's Keycloak realm roles. |
| `404 Not Found` | Warehouse ID does not exist. | Check the ID in the URL. |
| `409 Conflict` | Duplicate ID or referenced warehouse. | Use a unique ID or preserve the referenced warehouse. |

## Keycloak troubleshooting

### Postman reports `Client not found`

The `erp` realm was probably imported before the `mms-postman` client was added to `realm-export.json`. Keycloak does not overwrite an existing realm during startup.

Open `http://localhost:8080/admin`, log in with the Keycloak bootstrap administrator, and:

1. Select the `erp` realm.
2. Open **Clients** and create client `mms-postman` using OpenID Connect.
3. Enable **Standard flow** and require PKCE method `S256`.
4. Set **Valid redirect URIs** to `https://oauth.pstmn.io/v1/callback`.
5. Set **Web origins** to `https://oauth.pstmn.io`.
6. Save, request a new Postman token, and try again.

### Postman returns `403 Forbidden`

In the Keycloak admin console:

1. Select the `erp` realm.
2. Open **Users**, choose the user, and open **Role mapping**.
3. Assign `admin`, `inventory_manager`, or `store_keeper` for write tests.
4. Log out of Postman OAuth and obtain a new token so it contains the new role.

### Backend returns `401 Unauthorized`

- Confirm Keycloak is available at `http://localhost:8080/realms/erp`.
- Confirm the request contains `Authorization: Bearer <token>`.
- Confirm the token was issued by the `erp` realm.
- Obtain a new token because local access tokens expire after five minutes.
